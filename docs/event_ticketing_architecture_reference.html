Dependency rule (mandatory) — Dependencies point inward only: Presentation → Application → Domain. Infrastructure implements interfaces defined in Application. The Domain layer has zero external imports — no framework, no ORM, no HTTP library.
EventEvent creation constraints
  • End date must be strictly after start date
  • Maximum capacity must be greater than zero
  • Newly created event status is always Draft
  • Raises domain event EventCreated on success
EventEvent publishing constraints
  • Must have at least one active ticket category
  • Total ticket quota across all categories must not exceed max capacity
  • Only Draft → Published transition is allowed
  • A Cancelled event cannot be published
  • Raises EventPublished on success
EventEvent cancellation constraints
  • Only a Published event can be cancelled
  • A Completed event cannot be cancelled
  • All ticket categories become non-purchasable on cancellation
  • All Paid bookings must be flagged for refund automatically
  • Raises EventCancelled on success
EventTicket category constraints
  • Price must be ≥ 0; quota must be > 0
  • Sales end date must be ≤ event start date
  • Cumulative quota of all categories ≤ event max capacity
  • A disabled category is retained for historical data
  • Raises TicketCategoryCreated / TicketCategoryDisabled
BookingBooking creation constraints
  • Event must be Published
  • Ticket category must be Active
  • Current date must fall within the ticket's sales period
  • Quantity must be > 0 and ≤ remaining quota
  • A customer cannot have more than one active booking per event
  • Initial booking status is PendingPayment
  • Payment deadline is set to now + 15 minutes
  • Raises TicketReserved — quota is deducted immediately
BookingPayment constraints
  • Booking must have status PendingPayment
  • Current time must be before the payment deadline
  • Payment amount must exactly equal the booking total price
  • Total = (unit price × quantity) + service fee; cannot be negative
  • Total price is represented as the Money value object
  • On success: status → Paid; tickets are issued with unique codes; raises BookingPaid
BookingBooking expiry constraints
  • Only PendingPayment bookings can expire
  • A Paid booking cannot be expired
  • On expiry: reserved quota is released; status → Expired
  • Raises BookingExpired
TicketCheck-in constraints
  • Ticket must have status Active
  • Ticket must belong to the event being checked into
  • Check-in is only allowed on the event day or within the allowed window
  • A CheckedIn ticket cannot be used again
  • On success: status → CheckedIn; raises TicketCheckedIn
  • Invalid check-in must return a descriptive error without mutating ticket state
RefundRefund request constraints
  • Booking must have status Paid
  • None of the booking's tickets may be CheckedIn
  • Must be within the refund deadline (unless the event was cancelled)
  • If event is cancelled, refund is automatically allowed regardless of deadline
  • Raises RefundRequested
RefundRefund approval / rejection / payout
  • Approve: only if status is Requested → Approved; tickets → Cancelled; booking → Refunded
  • Reject: only if status is Requested → Rejected; rejection reason is mandatory; booking remains Paid
  • Pay out: only if status is Approved → PaidOut; payment reference must be recorded; terminal state

Core domain
Term Definition Layer
Event An activity created by an Event Organizer that customers can attend by purchasing tickets. Lifecycle: Draft → Published → Completed/Cancelled. Domain
TicketCategory A named type of ticket (Regular, VIP, Early Bird) with its own price, quota, and sales period. Owned by the Event aggregate. Domain
Quota The maximum number of tickets available in a given TicketCategory. Decremented on booking creation; restored on expiry. Domain
SalesPeriod The date range during which a TicketCategory can be purchased. Must end on or before the Event start date. Domain
Booking A temporary reservation of tickets created by a Customer. Holds status PendingPayment until paid or expired. Domain
PaymentDeadline Timestamp 15 minutes after booking creation. If payment is not completed in time, the booking expires and quota is released. Domain
Ticket Proof of attendance generated for each unit in a paid Booking. Unique TicketCode. Lifecycle: Active → CheckedIn/Cancelled. Domain
TicketCode Immutable, unique string used to validate a Ticket at the venue. Generated once upon payment. Domain
CheckIn The act of validating a Ticket at the gate. Transitions Ticket from Active to CheckedIn. A checked-in ticket cannot be reused. Domain
Refund A request to return the amount paid for a Booking. Lifecycle: Requested → Approved/Rejected → PaidOut. Domain
Money A value object representing a monetary amount and currency. Immutable; arithmetic returns new Money instances. Cannot be negative. Domain
Actors
Term Definition Role
EventOrganizer Creates events, manages ticket categories, approves/rejects refunds, and views sales reports. Organizer
Customer Browses events, creates bookings, pays, views tickets, and requests refunds. Consumer
GateOfficer Validates and checks in tickets at the event venue. Staff
SystemAdmin Triggers refund payout to customers and monitors operational processes. Admin
Application layer concepts
Term Definition Layer
Command An intent to change system state (e.g. CreateEvent, PayBooking). Handled by a CommandHandler which orchestrates the domain. Application
Query A request to read data without side effects (e.g. GetAvailableEvents). Handled by a QueryHandler returning a DTO. Application
DTO Data Transfer Object — a plain data structure used to communicate between layers. Contains no business logic. Application
Port An interface defined in Application that Infrastructure must implement (e.g. IPaymentGateway, INotificationService). Application
Status enumerations
Term Definition Context
Draft Initial status of a newly created Event. Not visible to customers. Event
Published Event is visible and bookable by customers. Event
PendingPayment Booking created; customer has 15 minutes to complete payment. Booking
Paid Booking payment completed; tickets have been issued. Booking
Expired Payment deadline passed without payment; quota released. Booking
Refunded Booking whose refund has been approved; tickets are cancelled. Booking
Active Ticket is valid and has not yet been used. Ticket
CheckedIn Ticket has been validated at the gate; cannot be reused. Ticket
PaidOut Terminal state of a Refund; money has been returned to the customer. Refund
